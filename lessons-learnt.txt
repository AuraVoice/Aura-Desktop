LESSONS LEARNT
==============

Purpose: Keep only durable engineering rules learned from real failures. Each lesson must remain
short enough to scan, must describe a reusable failure class, and must not become a chronological
debug diary. Unresolved audit findings are labeled "Required fix" instead of "Solution".

Date: 2026-07-03
Problem: The Tauri window became "Not Responding" during screen capture.
Issue: A synchronous Tauri command performed DXGI capture, image conversion, JPEG encoding, and
base64 work on the native message-loop thread. Windows could not pump window messages while that
work ran.
Solution: Make commands async by default. Put CPU-bound or blocking work in
tauri::async_runtime::spawn_blocking, and avoid encoding or serialization round trips when raw IPC
bytes are sufficient.
Justification: A non-async Tauri command shares the thread that keeps the native window alive.
Compilation cannot detect UI-thread starvation, so command threading is an architectural rule.

Date: 2026-07-04
Problem: Desktop voice repeatedly timed out even though the agent had joined and published audio.
Issue: The client waited for custom data messages that the backend never emitted. It also armed the
agent watchdog before token fetch and room connection, and initially missed agents already present
when Room.connect completed.
Solution: Verify wire contracts against the real producer and a working reference client. Use
LiveKit participant kind, participant attributes, transcription, and audio-track events. Scan
remoteParticipants immediately after connect, and arm join timeouts only after connect succeeds.
Route every terminal error through one durable logger with the room ID and error code.
Justification: Timeout tuning cannot repair an unreachable success condition. Observability and
protocol verification must precede timing changes.

Date: 2026-07-04
Problem: Overlay transitions could deadlock, repeat side effects, or leave the fullscreen pointing
window permanently click-through.
Issue: Overlay state locks were held across native window calls that synchronously re-entered event
handlers. Some direct state transitions did not emit the matching React event, and applied-state
caches could be updated inconsistently with the side effect they represented.
Solution: Hold state locks only for short reads or writes, never across window APIs. Every Rust
presentation transition must emit the event React uses to render it. Normal presentations must
restore cursor interaction defensively. Write applied-state caches only after resize, position,
show, or hide succeeds.
Justification: Native window APIs are re-entrant. State, native geometry, and React rendering must
either converge together or remain retryable after failure.

Date: 2026-07-04
Problem: The 3D avatar silently hung, framed the wrong pose, and swallowed clicks inside the drag
region.
Issue: Vite development pre-bundling broke DRACO's inferred decoder path, bind-pose bounds differed
from the animated pose, and a div with role=button was still treated as a window drag target.
Solution: Import the exact DRACO decoder assets and set their URLs explicitly. Evaluate the first
animation frame before measuring bounds. Use real button elements for interactive controls. Build
a small browser harness with visible bounds and frustum helpers before changing camera constants.
Justification: Build success does not validate the development loader, and correct camera math is
still wrong when it measures geometry that is not actually rendered.

Date: 2026-07-04
Problem: Sign-out could stall or allow an old async completion to reassert stale window state.
Issue: Cleanup awaited slow network-backed operations, and work started before sign-out could
finish after the account or foreground generation had changed.
Solution: Keep local sign-out bounded and independent of best-effort remote cleanup. Stamp async
work with an account or generation identifier and verify it again before applying completion state.
Justification: Cancellation alone is not a correctness mechanism. Stale completions must be made
unable to mutate the new session.

Date: 2026-07-05
Problem: Features existed in source but were unreachable from the states users actually entered.
Issue: Google sign-in and feedback were implemented without checking every real navigation entry
point, including returning-user screens that skipped onboarding.
Solution: Treat reachability as part of implementation. For every feature, trace at least one path
from each persisted landing state, not only the fresh-install path. Add a direct entry point or an
explicit reason the state cannot reach the feature.
Justification: Compiled code with no reachable control is equivalent to an unshipped feature.

Date: 2026-07-05
Problem: A cross-repository Google sign-in flow was correct on disk but failed for every live user.
Issue: Desktop, backend, and web deploy differently. The backend Docker build can include untracked
files, while the web deployment only receives committed and pushed files. Local source inspection
therefore gave a false picture of the deployed contract.
Solution: For cross-repository flows, verify every live endpoint and deployed artifact after an
approved deploy. Check route existence, request and response shapes, and the exact browser or app
handoff. Never equate "present locally" with "deployed".
Justification: A distributed feature is only as live as its least-deployed participant.

Date: 2026-07-05
Problem: A hardened CSP passed type-checking but broke Tauri IPC and runtime network behavior.
Issue: connect-src omitted runtime transport schemes such as ipc/http://ipc.localhost and was
derived from source-level URLs rather than the protocols the packaged webview actually used.
Solution: Build CSP allowlists from the packaged runtime, Tauri internals, Firebase, telemetry, and
backend transports. Verify IPC, authentication, voice, analytics, and error reporting in the real
webview after any CSP change.
Justification: CSP failures are runtime integration failures. Static checks cannot prove that a
webview can reach its native bridge or vendors.

Date: 2026-07-05
Problem: Installing Sentry risked replacing its panic hook, and development errors polluted the
same issue feed as installed-user failures.
Issue: std::panic::set_hook replaces the prior hook, and development sessions lacked a reliable
environment boundary in telemetry.
Solution: Chain panic hooks using take_hook before installing application logging. Disable remote
reporting in development and tag release events with environment and version.
Justification: Error reporting must preserve upstream crash capture, and an unresolved feed is only
useful when it represents real deployed users.

Date: 2026-07-08
Problem: A feature appeared absent because the installed release handled the launch instead of the
new development binary.
Issue: Dev and release shared the same Tauri single-instance identity. The old tray process accepted
the launch and displayed old bundled assets while the new dev process exited.
Solution: Keep single-instance behavior release-only. When behavior contradicts local source,
confirm the running artifact from asset origin, bundle hash, version, process path, and durable
logs before debugging feature code.
Justification: Testing the wrong binary produces convincing but meaningless evidence.

Date: 2026-07-08
Problem: A global hotkey collision crashed the entire tray application at startup.
Issue: Shortcut registration used ? in setup, so another process owning one key combination turned
a convenience failure into a process-killing setup error.
Solution: Register each shortcut independently, log and report failures, and continue booting with
tray access available.
Justification: Fail fast for corrupted invariants, not for optional operating-system integrations.
A missing shortcut should reduce convenience, not availability.

Date: 2026-07-08
Problem: Feedback log attachment silently failed because code hardcoded a log filename that did not
match tauri-plugin-log's generated filename.
Issue: Two call sites attempted to duplicate a value already derived from package metadata.
Solution: Derive generated paths and names from the same package or plugin source of truth. When a
file cannot be found, inspect the real directory instead of trusting comments or guessed names.
Justification: Replacing a wrong hardcode with a currently correct hardcode only delays recurrence.

Date: 2026-07-09
Problem: Adding more below-bar cards multiplied Rust booleans, applied caches, and duplicated
priority rules, causing redundant resize and focus side effects.
Issue: The same "which surface wins" decision existed in Rust geometry, Rust cache updates, and
React rendering. One applied cache was not updated on the normal success path.
Solution: React owns surface priority and sends one slot_height to Rust. Rust owns only native
geometry, with one applied_slot_height written after success.
Justification: Represent mutually exclusive UI with one discriminant or dimension. Parallel
booleans and mirrored priority logic create invalid combinations and forgotten cache updates.

Date: 2026-07-09
Problem: Subscription webhooks could permanently miss payments, restore revoked access, or ignore
chargebacks. This is an unresolved audit finding.
Issue: The event claim and entitlement write are separate Firestore operations. State is chosen
from event names even though Dodo retries can arrive out of order. Every event also assumes
data.metadata.firebase_uid, while dispute payloads identify only the payment.
Required fix: In one Firestore transaction, resolve a durable payment/subscription/customer to UID
mapping, reject stale transitions using authoritative payload state and event time, write the
entitlement, and create the billing event record. Test real Dodo fixtures for every event family.
Justification: Signature verification and duplicate detection are necessary but insufficient.
Billing correctness also requires atomicity, ordering defense, and resource-specific identity.

Date: 2026-07-09
Problem: A user can receive Pro without a durable entitlement or create multiple paid subscriptions.
This is an unresolved audit finding.
Issue: Missing entitlement documents resolve to Pro in enforcement paths, while trial stamping
depends on a cooperative client calling GET /entitlement. POST /billing/checkout does not reject or
reuse an existing paid billing relationship.
Required fix: All protected server entry points must atomically get or create the entitlement.
Checkout must enforce one billing relationship per UID, reuse dodo_customer_id, and be idempotent
across retries and devices.
Justification: Clients cannot be trusted to call initialization endpoints in order or to prevent
duplicate charges. Entitlement and billing uniqueness are server invariants.

Date: 2026-07-09
Problem: Desktop can serve one account's cached paid entitlement to the next signed-in account.
This is an unresolved audit finding.
Issue: The Tauri store uses one global cache key with no Firebase UID. Sign-out clears React state
but leaves the persistent cache, and a fresh cache suppresses the next backend fetch.
Required fix: Store the UID with the cached payload or key entries by UID. Require the current UID
when reading and writing, reject mismatches, and test paid-to-free account switching.
Justification: Every user-derived cache is part of the authorization boundary. TTL validation does
not replace identity validation.

Date: 2026-07-09
Problem: Trial and subscription lifecycle fields can disagree, and the launch migration can fail to
grant the promised trial. This is an unresolved audit finding.
Issue: Stored trialing status is trusted after trial_end_date, paid status is not reconciled with
expires_at, and the migration scans only existing entitlement docs while updating dates without
resetting eligible accounts to trialing.
Required fix: Resolve status and effective tier from authoritative dates and billing state. Migrate
from the users collection, upsert missing entitlement docs, reset eligible free users to trialing,
and test expired, missing, paid, cancelled, and concurrent cases in dry-run and apply modes.
Justification: A migration that updates dates but leaves a status that overrides them has changed
data without changing access.

Date: 2026-07-09
Problem: Mobile steering and checkout-return behavior can show prohibited or false purchase UI.
This is an unresolved audit finding.
Issue: Mobile treats locale country as store storefront. The web return page claims payment success
for both success and failure redirects, and targets an aura:// link that no current client handles.
Required fix: Use an authoritative storefront signal or default to SILENT. Render checkout state
honestly, verify entitlement before claiming unlock, and register and test a dedicated return deep
link before attempting it automatically.
Justification: Billing UI is a policy and trust boundary. Locale, redirect arrival, and an
unregistered URL scheme are not proof of storefront eligibility, payment, or app availability.

Date: 2026-07-09
Problem: The 2026-07-09 subscription audit findings above (13 total across the four repos) were
open: webhook uid resolution, event ordering, claim/merge atomicity, duplicate subscriptions,
missing-doc-grants-Pro, date-blind status, migration gaps, the desktop cache leak, locale
steering, the dishonest checkout return page, copy mismatches, ignored background pushes.
Issue: Resolved in this pass. Backend: reverse dodo_customers/dodo_subscriptions/dodo_payments
mappings + payment.succeeded and subscription.updated handling, one Firestore transaction for
claim + staleness + mappings + entitlement merge (last_billing_event_at guard), checkout 409 +
customer reuse, ensure_entitlement_doc get-or-create in every enforcement path, normalize_status
with a 3-day renewal grace, reset_trials rewritten to iterate users and reset status. Desktop:
entitlement cache keyed by uid, cleared on sign-out (clear_entitlement_cache). Web: return page
renders success/pending/failure from Dodo params and auto-fires aura://checkout only on success.
Mobile: steering from the backend-resolved country (silent when unknown), aura://checkout
registered on Android + iOS, background push persists a SharedPreferences refresh marker consumed
on resume, paywall copy matches enforced limits.
Non-obvious constraints hit along the way: a terminal webhook (dispute/refund) with no resolvable
uid must 500 for redelivery, never 200, because its payment mapping may land seconds later from a
payment.succeeded still in flight; a fake Firestore transaction must BUFFER writes and flush only
on success or atomicity tests pass vacuously; flutter test runs ENV=dev so SubscriptionService's
dev bypass shortcuts refreshEntitlement (tests need a @visibleForTesting state hook); the Flutter
repo's generated mockito mocks were stale after NotificationService grew entitlementUpdatedStream,
failing 23 unrelated tests until build_runner regenerated them.
Justification: Closes the audit trail; the constraints above are the ones a future pass would
otherwise re-discover the hard way.
