2026-09-03  macOS dictation reported "keyboard listener unavailable, restart" on every Mac

Problem: dictation did nothing on macOS, and Settings > Dictation told the user to restart
Aura, which changed nothing.

Issue: two halves. (1) The macOS CGEventTap callback ran the chord state machine but never
forwarded its signals to the dictation worker, and the tap was not even built when the voice
trigger was a registered chord, which became the macOS default in 1d671de. (2) The dictation

2026-09-03  a 90 minute cap killed notarytool mid-submission and erased the only evidence

Problem: the first full macOS release build compiled and signed cleanly, then emitted nothing

id, no status and no error, leaving nothing to separate a slow notary from a rejected upload

Issue: two things compounded. Tauri runs notarytool submit --wait and does not stream its

notarytool history, the one command that names a submission's real state, but sent it to
/dev/null.

rather than discarding it, so a forty second preflight dispatch reports whether an earlier
submission was Accepted, Invalid, In Progress, or never arrived. That listing immediately
named the real cause: the submission had reached Apple fine and was still In Progress more
than three hours later. Apple holds submissions it does not recognise for in depth analysis,
and this was the very first notarization this Developer ID had ever sent, so there was
nothing to recognise. Nothing in the config was wrong.

Justification: a timeout that kills the tool you are trying to observe turns a diagnosable
failure into a blank log. When a step's only output arrives at the end, size the cap for the
slowest case and keep a cheap out of band way to read the state afterwards. Output from a
command run purely to prove a credential is worth keeping; it is already the diagnostic.

hours or days, which is longer than any CI job should live, so the first notarization from a

Developer ID is hours of waiting, not a fix, and every submission after it is the usual two
to twenty minutes. Read notarytool history before spending a tag, once.


2026-09-04  The onboarding hotkey tour stopped accepting the shortcut after five minutes

Carbon-registered hotkey consumes the key before the webview sees it; the pass path lights

2026-09-05  the install guard relaunched itself 121 times and the app never opened

Problem: installing 0.14.1 from the website left the app permanently stuck. No window, no
crash, no error. Double-clicking Aura Desktop inside the mounted disk image did nothing
visible, for five minutes and counting. The only sign anything was happening at all was in
the log, one pair of lines every two and a half seconds, forever:
"install guard: running translocated, clearing quarantine on the real bundle" then
"install guard: moved to Applications, relaunching". A complete, valid, codesign-clean
0.14.1 was sitting in /Applications the whole time. The guard never once pointed at it.

Issue: macos_install.rs branched on the FACT of translocation and assumed the resolved
origin was an already-installed app that had merely kept its quarantine attribute, which is
the update case it was written for. On a first install the origin is the read-only disk
image, and there the quarantine is a MOUNT flag, not an xattr on the bundle:

  /dev/disk7s1 on /Volumes/Aura Desktop (hfs, read-only, quarantine, ...)
  xattr -p com.apple.quarantine "/Volumes/Aura Desktop/Aura Desktop.app"
    -> No such xattr    (exit 1)

So clear_quarantine ran xattr -d against a read-only filesystem (failed, warn only), then
asked xattr -p whether the attribute was still there, got "no", and returned true. It had
removed nothing because there was nothing to remove, and it reported success. relaunch_and_exit
then reopened the /Volumes path, macOS translocated it again because the mount is still
flagged, and the guard came straight back round. The success signal and the actual question
were never the same question.

Solution: branch on where the ORIGIN lives, not on whether the launch was translocated.
Installed origin keeps the repair path unchanged. An origin on the disk image or in Downloads
now falls through to the existing move_to_applications copy, silently, since macOS has
already made that launch useless for updates. Added a stamp file under Application Support
that caps the guard at one relaunch per 60 seconds: a relaunch that lands straight back shows
the "drag it in yourself" alert and RETURNS instead of exiting, so the app still opens and is
usable. clear_quarantine and repair_translocated both grew a comment saying what they cannot
be asked.

Justification: the loop was not a missing case so much as a predicate that could not fail.
"Does this bundle carry com.apple.quarantine" and "will this bundle be translocated again"
look like the same question and are not, and the one place they diverge is the exact place a
first install lands. Fixing only the branch would have left the next such divergence free to
spin the same way, which is why the relaunch cap went in alongside it and deliberately does
not exit: an app that opens without self-update beats an app that never opens. Worth noting
the guard itself is not the mistake - the same log carries
"install_pending_update: install failed: Read-only file system (os error 30)" from the build
before it, which is the failure it exists to prevent.

2026-09-05  the loop-breaker fired on the successful install it was meant to protect

Problem: caught in review, before shipping. The relaunch cap added above ran as the FIRST
thing in ensure_in_applications, before working out whether anything was actually wrong. The
happy path writes the stamp, sleeps two seconds and reopens, so the newly installed app came
up about three seconds later, saw a fresh stamp, and greeted a correct install sitting in
/Applications with an error log, a Sentry warning and a modal reading "Aura cannot update
itself from here". Every successful first install would have shown it.

Issue: a stamp that means "we relaunched" was being read as if it meant "we relaunched and it
did not work". Those are only the same question once you know the app is STILL misplaced,
which is exactly the check the breaker was sitting in front of.

Solution: resolve the bundle state first. Installed and not translocated returns immediately
and never looks at the stamp; only a launch that still needs fixing consults it. Two other
findings from the same review went in alongside: the silent disk-image copy asks for
confirmation whenever /Applications already holds a copy, because move_to_applications deletes
the destination and compares no versions, so opening an old disk image would have silently
downgraded and destroyed a newer install; and the new asset behind include_bytes! was still
untracked, which compiles locally and fails on any clean checkout, the same
untracked-file-never-ships trap the Aura-Web auth page hit.

Justification: guards that abort early are the easy ones to put in the wrong place, because
the failing path gets tested and the succeeding path does not. Ordering the check after the
"is anything actually wrong" question costs nothing and makes the false positive impossible
rather than unlikely. Worth noting none of the three were compile errors: cargo check and
clippy were clean the whole time.

2026-09-06  virtualizing the dictation list hid the row menu behind the rows

Problem: opening a row's overflow menu on the Dictation page showed only its bottom sliver.
The first two items were invisible and the destructive item was cut off. It looked like the
scroll container was clipping the menu, which sent the first look in the wrong direction.

Issue: it was paint order, not clipping. Windowing wraps every row in an element carrying
position:absolute plus transform:translateY, and transform creates a stacking context, so the
panel's z-index:20 was resolved INSIDE its own row's wrapper and could never rise above the
next one. The wrappers are positioned siblings at z-index:auto, so they paint in tree order and
every following row painted over the menu, each one opaque with its own backdrop-filter, which
is a second stacking context one level further in. The pre-virtualization design had solved
this by accident: one day card wrapped a whole day's rows, so one stacking context covered all
of them, and the comment explaining why that card was deliberately not overflow:hidden survived
on CSS that no longer matches anything. Switching the panel to position:fixed in place would
not have helped either, since transform and backdrop-filter ancestors are both containing
blocks for fixed children.

Two more defects from the same commit came out of the same trace. The virtualizer's scroll
element never scrolled, because nothing from .db-dictation-page down had a definite height, so
scrollHeight equalled clientHeight and getVirtualItems returned every row: the 400,000-node
hang the commit set out to fix was still there. And every row became the only child of its own
wrapper, so the adjacent-sibling divider rule could never match and every row matched
:only-child, losing the dividers and rounding all four corners of each one.

Solution: portal the panel into .db-app and place it from the trigger's rect, anchored by right
so the panel width never has to be measured and the old right-edge alignment survives; dismiss
it on scroll, since a fixed panel no longer travels with its row. Give the layout a real height
chain so the list scrolls itself, and re-key the dividers and radii onto the is-first/is-last
classes the same commit had already added to the wrapper.

Justification: a stacking context is invisible in the DOM and in the styles panel, and
transform is added for layout reasons by people who are not thinking about z-index at all. Any
popover that has to escape its row is one refactor away from being trapped, so the fix belongs
in the popover (leave the subtree) rather than in a z-index that the next transformed ancestor
will quietly defeat.

2026-09-06  dictation playback shipped with nothing anywhere that could decode it

Problem: playing a saved dictation on macOS always failed with "The audio for that dictation
could not be played." The same build played it on Windows. Everything the failure pointed at
was healthy: the command was registered unconditionally, no cfg(windows) sat on it or anything
it called, the clip decrypted, and the Blob was even given the correct audio/flac type, so it
was not the untyped-blob trap that WebKit is better known for.

Issue: clips are stored as FLAC and handed to the webview as FLAC, and nothing in the process
decodes FLAC. flacenc is an encoder; there is no decoder in Cargo.toml, in Cargo.lock, or in
package.json. So the decode was always the webview's job, and that only works where the webview
can do it: WebView2 is Chromium and decodes FLAC, WKWebView does not. The platform split was
never in our code, which is why grepping our code for it found nothing. Two things kept
disguising it. "Extract audio" writes the same bytes to disk with a .flac extension and macOS
plays that fine through Core Audio, so the storage looked healthy. And every other consumer of
these bytes is an uploader that posts them to a server, where something else does the decoding.

Solution: decode to 16-bit PCM with claxon and wrap it in a 44-byte RIFF/WAVE header inside
dictation_history_audio, and change the Blob type to audio/wav. The conversion sits in the
command rather than in read_clip, because read_clip also feeds the export, which must keep
writing a real .flac. Storage is unchanged, so there is no migration and nothing on disk is
re-encrypted. A clip that is not 16-bit is refused rather than cast, since that would need a
shift and would otherwise turn every sample into noise silently.

Justification: "which of our two platforms is this gated for" is the wrong first question when
a feature works on one and not the other. Nothing was gated here. The capability difference was
in a dependency neither platform's code mentions, and the module's own comments described the
bytes as something the dashboard "wraps in a Blob and plays", which reads like a complete plan
right up until you ask what performs the decode.
