2026-09-05  the install guard relaunched itself 121 times and the app never opened

Problem: installing 0.14.1 from the website left the app permanently stuck. No window, no
crash, no error. Double-clicking Aura Desktop inside the mounted disk image did nothing
visible, for five minutes and counting. The only sign anything was happening at all was in
the log, one pair of lines every two and a half seconds, forever:
"install guard: running translocated, clearing quarantine on the real bundle" then
"install guard: moved to Applications, relaunching". A complete, valid, codesign-clean
0.14.1 was sitting in /Applications the whole time. The guard never once pointed at it.

Issue: macos_install.rs branched on the FACT of translocation and assumed the resolved
origin was an already-installed app that had merely kept its quarantine attribute, which is
the update case it was written for. On a first install the origin is the read-only disk
image, and there the quarantine is a MOUNT flag, not an xattr on the bundle:

  /dev/disk7s1 on /Volumes/Aura Desktop (hfs, read-only, quarantine, ...)
  xattr -p com.apple.quarantine "/Volumes/Aura Desktop/Aura Desktop.app"
    -> No such xattr    (exit 1)

So clear_quarantine ran xattr -d against a read-only filesystem (failed, warn only), then
asked xattr -p whether the attribute was still there, got "no", and returned true. It had
removed nothing because there was nothing to remove, and it reported success. relaunch_and_exit
then reopened the /Volumes path, macOS translocated it again because the mount is still
flagged, and the guard came straight back round. The success signal and the actual question
were never the same question.

Solution: branch on where the ORIGIN lives, not on whether the launch was translocated.
Installed origin keeps the repair path unchanged. An origin on the disk image or in Downloads
now falls through to the existing move_to_applications copy, silently, since macOS has
already made that launch useless for updates. Added a stamp file under Application Support
that caps the guard at one relaunch per 60 seconds: a relaunch that lands straight back shows
the "drag it in yourself" alert and RETURNS instead of exiting, so the app still opens and is
usable. clear_quarantine and repair_translocated both grew a comment saying what they cannot
be asked.

Justification: the loop was not a missing case so much as a predicate that could not fail.
"Does this bundle carry com.apple.quarantine" and "will this bundle be translocated again"
look like the same question and are not, and the one place they diverge is the exact place a
first install lands. Fixing only the branch would have left the next such divergence free to
spin the same way, which is why the relaunch cap went in alongside it and deliberately does
not exit: an app that opens without self-update beats an app that never opens. Worth noting
the guard itself is not the mistake - the same log carries
"install_pending_update: install failed: Read-only file system (os error 30)" from the build
before it, which is the failure it exists to prevent.

2026-09-06  dictation playback shipped with nothing anywhere that could decode it

was not the untyped-blob trap that WebKit is better known for.

package.json. So the decode was always the webview's job, and that only works where the webview
can do it: WebView2 is Chromium and decodes FLAC, WKWebView does not. The platform split was

plays that fine through Core Audio, so the storage looked healthy. And every other consumer of
these bytes is an uploader that posts them to a server, where something else does the decoding.

command rather than in read_clip, because read_clip also feeds the export, which must keep

shift and would otherwise turn every sample into noise silently.

Justification: "which of our two platforms is this gated for" is the wrong first question when
a feature works on one and not the other. Nothing was gated here. The capability difference was

entry if a cleanup tool stripped it", which is true only for a missing entry.

is_enabled invites you to conflate them. The same shape as the optimistic-cache rule already in
CLAUDE.md: state that stands in for a side effect has to be checked against the side effect, not
against itself. Two consequences worth carrying. Verify a third-party predicate by reading its
implementation before building a skip on top of it, since both arms here were two lines and both
were weaker than the name promised. And note that the fix makes "whichever copy runs last owns

far side was busiest. Separately `another_interviewer` became reachable for the
first time and erases the live exchange without archiving it, and the archive in
`activate()` required `previousAnswer.trim()`, so any question whose answer never
rendered was silently dropped.

Solution: a speaker id is no longer a question boundary anywhere. `queueRemoteTurn`
merges unconditionally, the interim extension no longer checks the id, and a null
id counts as the same speaker rather than a different one (null means "overlap,
unknown", not "somebody else"). `another_interviewer` archives before it erases.
One `archiveActiveExchange` helper now serves both call sites and archives the
question even with an empty answer, and the card renders that as "No answer for
this one" instead of a hole. `rememberReflectionTurn` dedupes on turn id, which
is what produced the duplicate row carrying an earlier `at_ms` out of order.

Justification: silence ends a question, a relabel does not. Diarization is kept on
because the crosstalk logic and the speaker labels need it, but it is a display
and gating signal rather than a segmentation one. Turning diarize back off was
rejected: candidate-vs-interviewer attribution is physical (one ASR socket per
device), so diarization only distinguishes multiple interviewers and disabling it
would not have been a fix, only a second regression in the other direction.
`flushAnswerSync()` had to stay unconditional in `activate()` even though the
archive it guarded is now conditional; making it conditional lets a buffered delta
land after the reset and leak the old answer's tail into the new one.

Also logged along the way: `interview_companion_question_decision` already carries
`accepted`, `target`, `remote_speaker_present` and `speaker_overlap` - exactly what
identifies a dropped question - but went to PostHog only, which is why this needed
store forensics instead of a log read. It is now mirrored to `logInfo` as
`interview-decision`, with a character count and never the text.

2026-09-18 - The Screen Sight caption was being spoken as part of the answer

Problem: Screen Sight answers read badly. The prompt requires a first line of
`SCREEN|<caption>` that the client renders as "Looked at: ...".

Issue: `_read_screen_note` was only ever called AFTER the streaming loop, on a
buffer that the loop's own `yield buffer; buffer = ""` had emptied on every
iteration. So `decision["screen_note"]` was never set, the `screen_note` frame
never fired, and the marker line was streamed to the candidate as the opening
words of their own spoken answer. `awaiting_screen_note` was initialised and
consumed but never consulted inside the loop at all.

Solution: strip the marker inside the loop, before anything is yielded, mirroring
the `awaiting_decision` block directly above it. The post-loop call stays as the
final=True settle for a stream that ended before the marker resolved.

Justification: the fail-open contract is what makes this safe to do mid-stream - a
model that ignores the instruction returns ("", buffer) and keeps its whole answer,
and a partial prefix returns None so a real answer is never held hostage to a
marker that is not coming. Verified against full, absent and partial inputs before
wiring the new NEXT| line through the same path.

2026-09-18 - Interview answers were anchored on the resume even for conceptual
questions

Problem: asked anything, including pure concept questions, the answers reached for
the candidate's projects.

Issue: `resume_note` in `_answer_prompt` said "treat it as their real history and
answer with specifics from it", appended to the per-turn task for every action and
every intent. It sits in the volatile user message in last position, the highest
salience slot. The only counterweight was a clause on two rows of the cached
`intent_styles` table ("Do not plug in personal projects unless the question asks
for them"), which applies only if the model happened to write `concept` or
`compare` as its intent.

Solution: reword it so the resume is the source of truth for who the candidate is,
to be drawn on when the question is about them and explicitly ignored when the
question is conceptual, technical, hypothetical, or about the target company.

Justification: `focus_note`, five lines below in the same function, already ends
"When the question is generic, ignore focus." The fix is the symmetric clause, not
a new mechanism. The `grounded` flip that a non-empty resume triggers was left
alone deliberately: it is what stops fabrication, and weakening it re-opens the
gpt-oss hallucination the model-routing comment documents.

2026-09-18 - The screen-capture exclusion was asserted, never verified, and
failed in two opposite ways

Problem: the overlay is kept out of screen shares by one function, and nothing
anywhere could tell you whether it had worked. A user could be screen-sharing
the overlay with no sign of it.

Issue: three separate defects in the same short path.
`exclude_main_window_from_capture` returned the result of the set call and never
read the value back, so a call that reported success on an OS that ignored the
flag still read as applied. Its macOS body returned a hardcoded `Ok(())` around
`set_shares_screen_content`, which returns `()`, and whose `with_ns_window`
helper swallows a null NSWindow silently AND queues the closure when off the
main thread, so any Ok it produced was a statement about dispatch, not about the
window. The two call sites then took opposite wrong branches: `window_util.rs`
discarded the Result with `let _ =` and logged nothing, while `lib.rs`'s setup
used `?`, so a Windows failure aborted app launch entirely and the user got no
window at all. Nobody caught the `?` because the only branch that could return
Err was Windows, and the branch anyone testing on a Mac would hit could not fail
by construction. Affinity was also applied exactly once per window, at creation,
and never re-asserted across show, hide, move or monitor change, even though the
GWL_EXSTYLE hazard right beside it in `apply_result` is re-asserted for exactly
that reason.

Solution: read the value back on both platforms (`GetWindowDisplayAffinity`,
and a new main-thread-only `set_and_verify_shares_screen_content` that compares
`sharingType()` against what was asked for), record the verified outcome per
window label after the read-back agrees, re-apply and re-verify alongside the
existing style re-assert in `apply_result`, warn at both call sites instead of
swallowing or aborting, and surface it through `capture_exclusion_status` so the
Interview Companion card can say the overlay may be visible.

Justification: a guarantee the UI repeats to the user has to be a fact, not a
request. The read-back is what converts it, and it fails closed at every layer:
`Unknown` is not `applied`, a null NSWindow is an Err rather than a silent
no-op, and the JS helper returns false when the status cannot be read, because
claiming "hidden" on an invoke error would make the warning unreachable. The
`?` was downgraded deliberately: launching with a warning beats not launching.

2026-09-18  One boolean meant two things, and it disabled a model ban

Problem: Interview Companion kept answering conceptual, technical and
"why do you want to work here" questions by reaching into the candidate's
resume and steering back to their projects, which is exactly what the prompt
tells it not to do.

Issue: `grounded` in `interview_companion.py` was
`bool(candidate_evidence or payload.resume.strip())`, one flag serving two
unrelated decisions. It picked the system prompt AND it gated which models
could run. The 2026-09-16 fix that banned `openai/gpt-oss-120b` from ungrounded
turns (it had presented a JD's LightGBM fraud pipeline as its own experience)
keyed on that same flag, so attaching a resume silently re-admitted the model
to precisely the weakly-grounded turns it had been banned from. At the same
time a resume-only session picked up INTERVIEW_GROUNDED_SYSTEM, whose
"supplied evidence" means the verified brief and which never names
`candidate_resume` at all. The one rule scoping the resume lived in
`resume_note`, a clause concatenated mid-sentence into the volatile user
message, restated every turn, while the resume itself sat upstream in the
cached system prefix. `INTERVIEW_INTENT_STYLE["company"]` then told the model
to connect a company fact to candidate evidence, and `INTERVIEW_INTENT_RULE`
says the intent row wins where the two disagree, so on "why us" the
contradiction resolved in favour of the resume.

Verified from the session itself rather than from source: all 14 exchanges of
`interview-1789778116412-2` carry `unverified=1` (no reviewed brief), and every
one of its 16 answers ran on gpt-oss via Groq. Only a non-empty resume can
produce both at once.

Solution: split the prompt's notion of evidence from the model filter's.
`_evidence_kind` returns verified / resume_only / none; `_answer_system` takes
it; `resume_only` gets a new INTERVIEW_RESUME_ONLY_SYSTEM that names
`candidate_resume`, makes it the ceiling on personal claims, and says plainly
that it is not the subject of a conceptual, technical, hypothetical or
company question. `resume_note` now fires only for `verified`, where "which of
the resume and the brief wins" is a real question. The company intent row no
longer requires a candidate connection. `grounded` and the model filter are
untouched.

Justification: prompt-cache economics had quietly moved a safety rule away from
the data it governs (the resume rides the 1h cached prefix, so its rule was
pushed into the cheap volatile half to avoid churn). Putting the rule back next
to the resume costs one prefix change per session and nothing per turn. The
model filter was initially left alone as a knowing TTFT trade. An A/B eval then
showed that was wrong, which is the second half of this lesson.

Second issue, found by evaluating rather than reasoning: the prompt fix changed
nothing measurable. Probing the real model with a resume and no brief, the
intents everyone worried about (concept, compare, hypothetical, logistics) were
ALREADY clean before the change, because their intent rows carried the guard.
The only failing intent was `company`, and it failed for a bigger reason than
resume bleed: with no target context supplied, gpt-oss invented the interviewer.
It produced "Stripe's focus on developer-first payments" out of nothing, and in
another run promoted the candidate's OWN employer to the company interviewing
them ("I'm excited about Zephyrion because you're pushing..."). Adding an
explicit no-company clause to the system prompt narrowed this without closing
it: the model kept asserting soft facts ("your emphasis on responsible data
practices", "the recent push into edge computing").

Run head to head on the IDENTICAL prompt, Haiku refused all three: "I don't have
specific details about your company in front of me right now, so I want to be
straight with you - I'd rather ask what you're working on than guess." So the
binding constraint was the model, not the prompt.

Solution, second half: `_has_target_context` (company, role, target facts or JD
requirements - verification state irrelevant) now joins `not grounded` in the
Groq exclusion. A prepared interview keeps gpt-oss and its TTFT; only a session
with nothing at all about the company pays the fallback.

Justification, second half: the shape of this is the 2026-09-16 LightGBM
incident repeating, and the general rule it teaches is that a prompt rule cannot
reliably suppress a model's fabrication habit in a vacuum - if there is nothing
to say, only a model that will admit that is safe. The narrow gate was chosen
over "treat resume_only as ungrounded" because the latter would slow down
concept and walkthrough answers gpt-oss was already getting right. Worth keeping:
the eval was a throwaway harness that ran both arms by flipping one argument
(`kind="verified"` reproduces the old behaviour exactly), which is why measuring
cost minutes instead of a deploy and a real interview.

2026-09-18  A failed production deploy reported exit code 0

Problem: deploying the interview fix to Cloud Run appeared to succeed. The
command finished with exit code 0 and the last lines of output looked like a
normal tail. It had not deployed anything.

Issue: two faults stacked. The deploy was run as `bash deploy.sh ... | tail -80`
and the shell had no `pipefail`, so the pipeline's status was `tail`'s, not the
script's - a dead script reads as success. Underneath that, the run aborted in
the dictation storage preflight because it was executed from a clean worktree
carrying a copied `.env` whose GOOGLE_APPLICATION_CREDENTIALS points at
`service-account.json`, a file that was never copied alongside it. The image had
already been built and pushed to gcr.io by then, so the registry showed a fresh
digest even though `gcloud run deploy` had never run.

Solution: `set -o pipefail` before any piped deploy, copy the credential beside
the `.env` when deploying from a worktree, and verify against the live resource
rather than the script's own report: `gcloud run services describe` for the
serving revision and traffic split, then `docker run` the exact digest that
revision names and import the changed symbols inside it.

Justification: the registry digest and the exit code both said "shipped" while
production was still on the previous revision. The only claim that could not be
faked was running the deployed image and asking it what code it contains. The
same check is cheap enough to be the default: one `docker run --entrypoint
python` against the digest from `gcloud run revisions describe`. An image built
from a worktree is also a reminder that the build context is the directory, not
the git tree, so anything the runtime reads by path has to be present there too.

2026-09-18  Deepgram's request_id sits inside every Results frame, not on the
            closing Metadata frame the dictation socket never reads
================================================================================
Problem: schema v4's `recognition.providerRequestId` was wired end to end and
would have been `null` on every single desktop trace, forever, with nothing
logging a failure.

Issue: `asr/deepgram.rs` declared `request_id` at the TOP LEVEL of `ServerFrame`,
which is where the standalone `{"type":"Metadata","request_id":...}` frame carries
it. That frame arrives after Deepgram closes the stream, and `run_socket` breaks
out of its loop the moment the `from_finalize` Results frame lands, so the
dictation path never reads it. The interview path does, which is why the shape
looked already proven. Nothing would have surfaced this: serde drops undeclared
fields silently, an absent optional field is a valid payload to the backend, and
the column would simply have stayed empty.

Solution: declare the nested `metadata` object that rides inside every `Results`
frame and read `metadata.request_id` from there, first non-empty wins, with the
`dg-request-id` upgrade-response header and the closing frame as fallbacks.

Justification: this was found by reading two consumers that already ship rather
than by reasoning about the wire format. `Aura/backend/src/services/meetings/
deepgram.py:219` confirmed the word field names (`punctuated_word or word`,
`start`, `end`, `confidence`) and showed it derives the utterance confidence by
averaging per-WORD confidences rather than trusting an alternative-level field,
which became the fallback here. The vendored official plugin at
`livekit/plugins/deepgram/stt.py:818` was decisive: it reads
`data["metadata"]["request_id"]` inside its `Results` branch. Two independent
shipping readers beat any amount of careful thinking about a JSON shape. The
general rule: when adding a provider field, find an existing consumer of that
provider in the tree and match it, because a field that silently never arrives
looks exactly like a field that is working.

2026-09-20  Two tokens minted together must not be pushed in a chain: the second
            push was what made sharing work, and the first could veto it
================================================================================
Problem: `usePolishCredential`'s cycle mints one Firebase ID token and pushes it
to two Rust holders, `pushPolishCredential` then `setUploadToken`, both awaited
in sequence. Any throw from the first (an unregistered command, an IPC failure)
skips the second entirely.

Issue: with no upload token, `upload.rs` returns 401 for every attempt by design,
`classifyUploadFailure` maps that to `signedOut`, and the drain sets `stop = true`
on every tick. Dictation sharing is then completely dead with
`lastErrorReason: "signed_out"`, no attempt burned on any row, and nothing in any
log saying the upload token was the missing piece rather than the session. The
polish command has been gated behind `#[cfg(windows)]` once before, which is
exactly the failure that produced this shape: see the `usePolishCredential.ts`
retry loop in the platform-gating lesson above.

Solution: push the upload token FIRST, then polish. One line swapped.

Justification: `Promise.allSettled` was the obvious fix and is wrong here. The
cycle's return value drives the retry schedule, so settling both would either
swallow a polish failure forever or need a partial-failure policy the pump has no
vocabulary for. Ordering gets the same independence for free: a polish throw still
retries the whole cycle, and by then the upload token is already in place. The
teardown path in the same file already used `allSettled` for both clears, which is
correct there because a clear has nothing to retry. The general rule: when one
mint fans out to N consumers, a sequential await chain silently ranks them, and
the last one in the chain is the one that dies quietly.

2026-09-21  A spoken-answer prompt cannot be asked for code, and "half the
            meeting" was a missed start rather than an early stop
================================================================================
Problem: three complaints from one Interview Companion session. A LeetCode
screenshot came back as a paragraph explaining the problem instead of a
solution. The follow-up "now give me the code" answered "I cannot see your
screen, I don't have any information". And a meeting recorded about half its
length.

Issue, one per complaint, none of them where it looked:

The code case was not a model failure and no amount of re-prompting the
question would have fixed it. Three layers each independently forbid a code
block: INTERVIEW_VOICE_RULE ("write ONLY the words they say out loud"),
INTERVIEW_SPOKEN_RULE ("never any formatting a person cannot say aloud",
"never write more than one paragraph"), and a 480-token ceiling, with the
volatile task line restating "in one paragraph" every turn so the cached rule
could not be argued with. A fenced block is by definition formatting nobody
can say aloud. The feature was structurally incapable of the thing it was
being asked for.

The refusal string does not exist in the interview handler or in any of its
prompts. It belongs to the Buddy voice agent's screen_context_control.py, so
the first instinct was that the follow-up had left the card. It had not: the
Ask button calls evaluate(..., "suggest"), and interview_companion.py filters
the vision-less Groq primary out for action == "screen_sight" ONLY. The
follow-up therefore ran on gpt-oss-120b, which has no vision at all, holding a
15-word caption. It improvised a refusal that happened to match another
subsystem's guardrail word for word, which is the part that would have sent a
second investigation down the wrong path.

The meeting was not truncated. capture_runs said stopped_by_user, 1320 s, five
of five segments uploaded, and the log put the stop four seconds after the
call's own end. The missing half was at the FRONT: "ambient call seen
(google-meet)" fired for the first time twenty-two minutes into the call,
because detect.rs matches window titles and, as its own comment says,
"EnumWindows exposes only a browser's active tab title". A Meet in a
background tab is invisible, so the prompt only appeared when the tab came
forward.

Solution: a fourth register (INTERVIEW_SCREEN_CODE_RULE) on the volatile
system for screen_sight only, where it is the later word on rules that live in
the cached prefix, plus a screen-only 1400-token ceiling and the sentence
budget dropped for that one action. INTERVIEW_SCREEN_RECALL_RULE for the
caption-only turn. One composer in the card with a sticky screen toggle, so
every send captures fresh and a follow-up reaches a vision model. And a
microphone probe in detect.rs: a browser holding an active WASAPI capture
session is a call, whichever tab it is in.

Justification: the spoken rules are right for every other answer, so they were
overridden for one action rather than loosened. The token ceiling's comment
says the cap "cannot vary by intent" because intent is chosen mid-stream; that
argument does not reach action, which arrives in the request, and the
distinction is what let the ceiling move safely. The sticky toggle beats
retaining the last frame: re-capturing has no staleness window and adds no
retention question. The mic probe reports "browser-call", never a guessed
platform, because it knows the process and not the site, and it carries a
fixed title because call_key hashes the title and the browser's own would
change on every tab switch. Two forensic notes worth keeping: capture_runs
stores complete_reason, started_at_ms and total_duration_ms in PLAINTEXT, so
"why did this recording stop" is one SQL query with no decryption; and the
desktop log is UTC while that table is localtime, which is a seven hour trap
when lining the two up.
