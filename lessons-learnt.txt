it called, the clip decrypted, and the Blob was even given the correct audio/flac type, so it
was not the untyped-blob trap that WebKit is better known for.

Issue: clips are stored as FLAC and handed to the webview as FLAC, and nothing in the process
decodes FLAC. flacenc is an encoder; there is no decoder in Cargo.toml, in Cargo.lock, or in
package.json. So the decode was always the webview's job, and that only works where the webview
can do it: WebView2 is Chromium and decodes FLAC, WKWebView does not. The platform split was
never in our code, which is why grepping our code for it found nothing. Two things kept
disguising it. "Extract audio" writes the same bytes to disk with a .flac extension and macOS
plays that fine through Core Audio, so the storage looked healthy. And every other consumer of
these bytes is an uploader that posts them to a server, where something else does the decoding.

Solution: decode to 16-bit PCM with claxon and wrap it in a 44-byte RIFF/WAVE header inside
dictation_history_audio, and change the Blob type to audio/wav. The conversion sits in the
command rather than in read_clip, because read_clip also feeds the export, which must keep
writing a real .flac. Storage is unchanged, so there is no migration and nothing on disk is
re-encrypted. A clip that is not 16-bit is refused rather than cast, since that would need a
shift and would otherwise turn every sample into noise silently.

Justification: "which of our two platforms is this gated for" is the wrong first question when
a feature works on one and not the other. Nothing was gated here. The capability difference was
in a dependency neither platform's code mentions, and the module's own comments described the
bytes as something the dashboard "wraps in a Blob and plays", which reads like a complete plan
right up until you ask what performs the decode.

2026-09-07  Launch at login pointed at a dev binary for four days, and nothing repaired it

Problem: after a macOS restart the app came up wrong. Screen capture was denied, and an update
prompt offered a version it never installed. It looked like the app had failed to launch. It had
not. launchd fired the login item exactly as configured; the login item just named the wrong

The tell was in one log file. Same identifier, same path, two different versions:
"found 0.15.0 -> 0.15.5" at boot, "found 0.15.4 -> 0.15.5" on a manual launch minutes later. A
dev build is ad-hoc signed, so TCC treats it as a different app and every grant is missing, and
its updater cannot replace a bundle it is not running from.

Issue: two defects, and the second is the one that made it last. lib.rs guards the automatic path
with !cfg!(debug_assertions), but the tray toggle and the Settings row reach autostart::set
directly, unguarded, so a `tauri dev` session could write its own current_exe() into the entry.
Then apply() only acted on a state change, `if current != enable`, and asked
tauri-plugin-autostart's is_enabled() what the current state was. That call cannot answer the
question being asked of it. In auto-launch 0.5.0 the macOS arm is
`Ok(self.get_file().exists())`, a bare existence check on ~/Library/LaunchAgents/<name>.plist,
and the Windows arm looks the Run value up by NAME. Neither ever compares the stored program
path. So a wrong entry read as "already enabled", the write was skipped, and the entry survived
three reinstalls and two updates untouched. The module's own doc comment claimed it "repairs the
entry if a cleanup tool stripped it", which is true only for a missing entry.

Solution: apply() re-asserts the entry whenever it should be on, `if enable || current`, rather
than only on a transition. Both backends overwrite in place (fs::File::create truncates the
plist, set_value overwrites the Run value), so this is idempotent and corrects a wrong path as a
side effect. Disabling still skips when no entry exists, because the crate treats that as an
error, which is what the original short-circuit was actually protecting. A cfg!(debug_assertions)
early return was added to apply() itself rather than to its callers, so the tray toggle, the
Settings row and anything added later are all covered by one guard. Deliberately no plist parsing
and no registry read: reading the path back would have meant winreg or an unsafe RegGetValueW on
Windows, and the Windows tree cannot be cross-compiled from a Mac, so that would have been
unverifiable code bought for nothing.

Justification: the short-circuit was not wrong about caching, it was wrong about what its cache
meant. "An entry exists" and "the entry points at me" are different claims, and a boolean named
is_enabled invites you to conflate them. The same shape as the optimistic-cache rule already in
CLAUDE.md: state that stands in for a side effect has to be checked against the side effect, not
against itself. Two consequences worth carrying. Verify a third-party predicate by reading its
implementation before building a skip on top of it, since both arms here were two lines and both
were weaker than the name promised. And note that the fix makes "whichever copy runs last owns
the login item" literally true, which is correct with one install and a coin flip with two: a
second /Applications bundle sharing the identifier reintroduces the same symptom by a different
route, so the duplicate had to go as part of the fix, not as tidying.

2026-09-08  Dictation failed on the first press after a long idle: the credential timer lives in a webview

Problem: after the Mac had been idle or asleep, the first chord hold showed "Dictation credential
unavailable. Nothing was typed." and the second hold a few seconds later worked. Reproduced six
times in one day's log, always the same shape: last refresh, a gap, phase=failure
failure=unavailable, and a state=stored line ONE second after the failure.

Issue: two clocks were wrong. The transcription token is minted for 300s and refreshed by a
setTimeout in the always-hidden overlay webview (useCredentialPump.ts). WebKit stalls those
timers through system sleep and throttles them while the window is hidden, so the token was
dead for anything from minutes to hours before the timer fired, and Rust had no way to ask for
one: it failed the hold, and the timer then happened to run. Separately, ScopedToken measured
expiry with Instant, which on macOS is CLOCK_UPTIME_RAW and does not advance during sleep, so a
token minted before a two hour nap still looked fresh to Rust after it while the provider had
long since expired it; that path surfaced as the different "could not sign in to transcription"
caption.

Solution: ScopedToken keeps expiry as SystemTime, the clock the issuer actually uses. When the
chord finds no credential while signed in, run_utterance emits dictation-credential-needed to
the overlay, shows the listening pill, and waits up to three seconds for the token while still
honouring release and cancel; the pump listens for that event and mints immediately unless a
mint is already in flight. Release before it lands says "Dictation was reconnecting. Hold the
keys and try again."; a timeout keeps the old caption.

Justification: a hidden webview's timer is not a scheduler for anything a native code path
depends on, and Instant is not a wall clock on macOS. The log already carried the whole story
(the stored line landing a second after the failure) but nothing read it that way until the
failures were lined up against the refresh cadence. The verification is behavioural: sleep the
Mac past the token's life, wake, press once, and the first hold must transcribe.
