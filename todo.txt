2. STATE MACHINE / MULTI-ENTRY-POINT EDGE CASES
------------------------------------------------
This is the "one screen, many ways in" audit. overlay.rs is reached from: the global hotkey,
tray left-click, tray menu, second-instance launch (summon), Firebase auth state changes,
voice session start/end, screen-sight's point_at/cancel_pointing, and Windows' own
WindowEvent::Moved. Every pair of these that can fire close together is a real edge case.

[ ] P0 - Fix or explicitly document the pre_pointing fallback in cancel_pointing: if
    pre_pointing is somehow None when a pointing takeover ends, it falls back to
    (Hidden, Setup) - losing the Bar variant for an already-signed-in user. Why: point_at
    always sets pre_pointing if it's None, so this should be unreachable today, but there's
    no test pinning that invariant and no logged warning if the fallback ever fires, so a
    future change to point_at's call sites could silently regress a signed-in user back to
    the setup-sized panel with no error anywhere to catch it.

[ ] P0 - Decide and implement a recovery path for OverlayState mutex poisoning. Why: every
    call site uses `.lock().unwrap()`; if any code path ever panics while holding that lock
    (a Rust panic, not a Result::Err), every future `.lock().unwrap()` anywhere in the app
    panics too, since a poisoned std::sync::Mutex stays poisoned forever. Given this repo's
    own history (two logged incidents were mutex/thread deadlocks before being fixed), a
    poisoned-lock permanent-freeze is the same failure class recurring in a new shape.
    Minimum fix: use `.lock().unwrap_or_else(|e| e.into_inner())` at every call site so a
    single panicked critical section can't brick the whole overlay for the rest of the
    process's life.

[x] P0 - Audit and log store I/O failures instead of silently defaulting. Why:
    auth_cache.rs's has_cached_session returns `false` on any store-open error, which on a
    transient disk/permissions error would show a signed-in user the pairing screen at cold
    start (a confusing, support-ticket-generating false negative) with no log line to explain
    why. overlay.rs's persist_center silently no-ops on store failure too. Both already call
    `error!()` on the Rust side per logging.rs, but neither is currently instrumented as a
    PostHog/Sentry event, so a real-world occurrence during beta would be invisible unless a
    tester happens to also check their log file.
    DONE 2026-07-07: auth_cache.rs, overlay.rs persist_center, and autostart.rs all report
    store-open failures to Sentry now (v0.1.5), on top of the local error!() lines.

[ ] P0 - Test and fix concurrent/racing trigger combinations explicitly (this is exactly the
    shape of every incident in lessons-learnt.txt so far): hotkey pressed the instant
    point_at's takeover starts; tray click or second-instance launch while a voice call is
    mid-teardown; Ctrl+Shift+D fired during the pairing flow (before any session exists);
    minimize_to_pill immediately followed by the call ending server-side (race between the
    user's minimize click and set_voice_active(false)); rapid hotkey double-press faster than
    apply()'s window calls can complete. Why: `hotkey_pressed`'s match has a bare `_ => {}`
    for Pointing (deliberate) but every other combination above is either untested or only
    incidentally correct because of the belt-and-suspenders fixes already logged - a
    regression in any of those fixes reopens the exact bug class already paid for once.

[ ] P1 - Multi-monitor/DPI edge cases: monitor unplugged or replugged mid-session (does
    user_center recovery on next launch handle a since-changed arrangement correctly, not
    just at cold start via load_persisted_center), DPI change while the app is visible
    (Windows can hot-change scale factor when a window crosses monitors with different
    scaling), and point_at's target monitor being disconnected between the agent's
    element.point event and the takeover actually applying. Why: active_display_bounds
    already has a documented triple-fallback (cursor monitor -> primary monitor -> hardcoded
    1920x1080), which itself signals this class of failure was anticipated but not yet
    tested end to end.

[ ] P1 - Auth/session edge cases: Firebase token refresh failure while a call is live,
    session revoked server-side mid-session, and sign-out fired from every entry point
    (VoiceBar button, Ctrl+Shift+D, tray, OS shutdown/log-off) while a LiveKit call is
    active - confirm each one tears down the LiveKit room cleanly rather than orphaning a
    backend session. Why: AuthProvider.tsx's onAuthStateChanged handler assumes it always
    fires promptly and doesn't currently guard against a stale user object mid-call; an
    orphaned backend/LiveKit session on the failure path is a real cost (agent compute
    running with nobody listening).

[ ] P1 - App relaunch or crash while a call or screen-sight session is active: confirm state
    recovers cleanly (Hidden/Panel per cached session, not some stale Pointing/Pill
    leftover) and that the abandoned backend/LiveKit room gets cleaned up server-side rather
    than lingering. Why: overlay-window.json and auth-state.json both persist across
    restarts by design, but neither currently distinguishes "clean exit" from "crashed mid-
    call," so a crash during Pointing could plausibly leave stale state that's only ever
    been exercised via the normal apply()-mediated paths.

[ ] P1 - Windows sleep/resume, lock/unlock, and fast user switching: verify the LiveKit
    connection, mic capture, and overlay window all recover (or fail loudly with a retry, not
    silently) across a sleep/resume cycle. Why: this is untested today and a very common real
    -world interruption for a companion app that's expected to be running continuously in
    the background.


3. DEVICE / ENVIRONMENT COMPATIBILITY
---------------------------------------
[x] P0 - Detect a missing WebView2 runtime and prompt the user to install it (Microsoft's
    Evergreen bootstrapper) instead of failing silently or crashing. Why: WebView2 isn't
    preinstalled on every Windows image (especially older/locked-down corporate ones), and
    this app has no functionality at all without it - a blank or crashing first launch for a
    beta tester with no explanation is the worst possible first impression and the hardest
    bug to get a useful report about.
    DONE 2026-07-07: tauri.conf.json bundles the Evergreen bootstrapper
    (webviewInstallMode: embedBootstrapper), so the installer handles it.

[ ] P0 - Get a Windows code-signing certificate (Authenticode; EV strongly preferred, since
    EV certs skip SmartScreen's reputation-building period that a plain OV cert still has to
    earn one download at a time) and wire it into release.yml. Why: TAURI_SIGNING_PRIVATE_KEY
    in release.yml signs update manifests for the Tauri updater, which is a completely
    different key from an Authenticode code-signing certificate for the .exe/.msi itself -
    right now the installer is very likely unsigned, which means every beta tester sees a
    Windows SmartScreen "Unknown publisher" warning on first run, a significant beta-adoption
    killer.

[ ] P1 - Audio device edge cases: no microphone present at all, multiple mics with the OS
    default changing mid-call, Bluetooth headset connect/disconnect mid-call, and another app
    holding the mic in exclusive mode. Why: useVoiceBar.ts's retry logic already special-
    cases "mic-access errors that need user action" per lessons-learnt.txt, but the specific
    device-change-mid-call scenarios aren't confirmed handled, and a public beta will surface
    every one of these within the first week.

[ ] P1 - Corporate/managed-machine environments: global hotkey registration blocked by
    endpoint policy, firewall blocking LiveKit's UDP/TURN fallback, and HTTP proxy
    environments breaking TLS to the backend, PostHog, or Sentry. Why: capabilities/
    default.json scopes the webview's http access tightly (good for security), but a
    corporate TLS-inspecting proxy can still break every one of those calls in ways that look
    like "the app is just broken" with no obvious cause from a support ticket alone.

[ ] P1 - Keyboard layout edge cases: the three global hotkeys are defined by physical key
    code (Code::KeyB/D/S per hotkeys.rs), which is layout-independent by design, but confirm
    this is actually correct on non-US physical keyboard layouts (AZERTY, QWERTZ, etc), not
    just non-US input methods on a US physical keyboard. Why: Tauri's global-shortcut plugin
    maps Code variants to physical scan codes, which is the right choice for hotkeys meant to
    be muscle memory regardless of layout, but it's unverified on non-US hardware today.

[ ] P2 - GPU/driver variance: verify the three.js AvatarPill renders acceptably (or degrades
    gracefully to a static frame/text fallback) on integrated GPUs, in a VM with no real GPU
    (software/WARP rendering), and on old/unsupported GPU drivers. Why: the pill is a WebGL
    scene rendered inside WebView2's own Chromium; a GPU that can't do WebGL well (or at all)
    would currently just show a broken or invisible pill with no fallback path.

[ ] P2 - Windows ARM64 and Remote Desktop / VM sessions. Why: lower priority than the above
    since they're a small fraction of the likely beta population, but worth a pass before
    GA - RDP sessions in particular sometimes change how always-on-top, click-through, and
    global hotkeys behave.

--------------------------------------
[x] P0 - Add a release notes template (What's new / Fixed / Known issues / Rollback
    instructions) attached to every GitHub release. Why: release.yml currently creates a
    releaseDraft with no body content beyond the auto-generated title - a beta tester hitting

    unannounced relaunch, and never install mid-call.

[ ] P1 - Separate a beta update channel from a stable one (e.g. a `-beta` tag suffix and a

    updater protocol has no built-in support for this (already flagged as a TODO in

    ecosystem; the rollback runbook above is the higher-leverage, lower-effort mitigation to
    have in place first.
